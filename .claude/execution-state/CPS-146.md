## Decisões técnicas registradas
- Refatoração real: TravelController não chama mais NotificationService
  direto — publica NotificationEvent via ApplicationEventPublisher;
  NotificationEventRelay (@TransactionalEventListener AFTER_COMMIT) publica
  no RabbitMQ; NotificationConsumer (@RabbitListener) é quem persiste a
  Notification (via NotificationService, agora retornando Notification em
  vez de void) e dispara o push.
- PushTarget: destinatário polimórfico reaproveitando NotificationRecipientType,
  campos separados para Android (topic) e Web (endpoint/p256dh/auth).
- POST /push-targets é idempotente (upsert por recipiente+plataforma+
  topic/endpoint) — achado do /code-review, corrigido antes do commit.
- WebPushDispatcher usa nl.martijndwars:web-push (BouncyCastle + jose4j
  precisaram ser adicionados explicitamente como compile, não vêm
  transitivos apesar de declarados na lib).
- Chaves VAPID de DEV geradas localmente, com default via application.properties
  (mesma convenção do jwt.secret) — produção deve sobrescrever via env var.
- CI (GitHub Actions) ganhou um serviço RabbitMQ efêmero — sem isso os testes
  quebrariam lá também (mesmo motivo do bloqueio original).
- Testes de NotificationControllerTest (CPS-145) ajustados para aguardar a
  entrega assíncrona em vez de assumir sincronia; corrigido também um race
  real de "aquecimento" de conexão AMQP (mensagem 1 pode chegar depois da
  mensagem 2 se a conexão ainda não estiver aberta).
